# agterm-kit

Обвязка для терминала [agterm](https://github.com/umputun/agterm): shell-функции и скрипты,
которые опираются на его модель воркспейсов и сессий и на `agtermctl`.

Внутри:

- `wt`: git worktree для текущей репы или репы воркспейса agterm;
- `ask`: вопросы агентов (Claude Code, Codex, OpenCode) с вариантами ответа в HTML-оверлее agterm.
- [GUI и cookbook](workflows/README.md): проекты, задачи и worktree с Claude, рецензии
  документов, dashboard, восстановление разговоров и компаньоны. Установка: `make install-gui`.
  Панель задач: **Ctrl+Shift+W**, оформление в стиле JetBrains New UI Dark.
- `lb-limits`: лимиты пула аккаунтов agent-lb в статус-строке Claude Code.
- `stages`: стадия работы агента под каждой сессией и доска по всем сессиям.

## wt

`wt fix-login` внутри клона `qa-tools` (или в воркспейсе agterm с именем `qa-tools`) делает следующее:

1. Берёт репу из текущего каталога, а вне git-репы ищет клон `qa-tools` по имени воркспейса
   в каталогах из конфига.
2. Подтягивает базовую ветку с origin.
3. Создаёт ветку `fix-login` и worktree рядом с клоном: для `~/git/qa-tools` это
   `~/git/worktrees/qa-tools/fix-login`.
4. Переименовывает текущую сессию agterm в `fix-login` и запускает в ней Claude Code.

Параллельная задача в той же репе оказывается в отдельном каталоге и отдельной ветке,
а основной клон остаётся как был.

```
wt [-a claude|codex|none] <постфикс>   создать worktree и запустить агента
wtl                                    все worktree по всем репам
wtrm [<репа>] <постфикс>               удалить worktree, ветку и пустые каталоги
wt-migrate [--apply] <старый root>     перенести worktree из прежней общей папки
wt -h                                  справка с текущими значениями конфига
```

### Установка

Нужны zsh, git, jq, agterm с установленным `agtermctl` (Help ▸ Install Command Line Tool…).
fzf необязателен: он нужен `wtrm`, когда имя репы совпадает частично с несколькими.

```sh
git clone https://github.com/tiptop32/agterm-kit ~/my_git_reps/agterm-kit
~/my_git_reps/agterm-kit/install.sh
```

`install.sh` делает следующее:

- ставит симлинк `~/.config/zsh/wt.zsh` на `wt/wt.zsh` из репозитория. Прежний файл
  сохраняется рядом как `wt.zsh.bak.<время>`;
- создаёт `~/.config/agterm-kit/wt.conf` из `wt/wt.conf.example`, если конфига ещё нет;
- подсказывает строку для `~/.zshrc`, если `wt.zsh` там ещё не подключён:

  ```sh
  source ~/.config/zsh/wt.zsh
  ```

Повторный запуск ничего не ломает. После `git pull` в репозитории новая версия подхватывается
в новых шеллах без переустановки: подключён симлинк.

### Конфиг

`~/.config/agterm-kit/wt.conf` (другой путь задаёт `WT_CONFIG`):

```ini
# Где лежат клоны реп. Ключ можно повторять.
repos = ~/git
repos = ~/work/git
repos = ~/warp       # можно указать и сам клон
```

- Формат «ключ = значение». Строка с `#` в начале и хвост после ` #` считаются комментариями.
- `~` и `$HOME` раскрываются в начале пути, `..` схлопывается. Конфиг не исполняется как
  shell-код.
- Значение `repos`: каталог с клонами или сам клон. Элементы просматриваются по порядку.
  Если репа с одним именем есть в двух местах, выигрывает первое.
- `repos` нужен для поиска по имени воркспейса, `wtl` и `wtrm <репа>`. Для `wt` внутри
  git-репы прописывать её в `repos` не обязательно.
- Конфиг читается при каждом вызове: правка действует сразу, перезапускать шелл не нужно.
- `WT_REPOS` (несколько путей через двоеточие, как в `PATH`) перекрывает `repos`.
- Прежний ключ `root` и переменная `WT_ROOT` больше не действуют. `wt` предупреждает о них
  и работает дальше; уберите их и перенесите старые worktree командой `wt-migrate`.

### Где лежат worktree

Worktree лежит рядом со своей репой: `<родитель репы>/worktrees/<репа>/<постфикс>`.
Каталог `worktrees/` создаётся при первом `wt`, а `wtrm` удаляет его, когда он опустел.

| Клон | Worktree `fix-login` |
|---|---|
| `~/x5/git_reps/cloud-autotests` | `~/x5/git_reps/worktrees/cloud-autotests/fix-login` |
| `~/my_git_reps/agterm-kit` | `~/my_git_reps/worktrees/agterm-kit/fix-login` |
| `~/warp` (сам клон в `repos`) | `~/worktrees/warp/fix-login` |

Рабочие репы из одной папки делят один `worktrees/`, личные — свой. Одноимённые клоны
из разных папок не мешают друг другу. В `worktrees/` нет `.git`, поэтому в списке реп
он не появляется. Симлинки в пути раскрываются: место определяет настоящий каталог клона.

### Перенос из общей папки

До этой версии все worktree лежали в одном `root`, например `~/wt/<репа>/<постфикс>`.
`wt-migrate` переносит их на новые места:

```sh
wt-migrate ~/wt            # план: что куда переедет и что будет пропущено
wt-migrate --apply ~/wt    # перенести
```

- Переносятся только worktree реп из `repos`, лежащие внутри указанного каталога по схеме
  `<старый root>/<репа>/<постфикс>`. Если старый root указан на уровень глубже или выше,
  worktree пропускаются с подсказкой, а уже лежащие на новом месте не трогаются.
  Каталоги, которые не оказались worktree этих реп, wt-migrate показывает и не трогает.
- Перенос делает `git worktree move`, поэтому git сам обновляет свои ссылки. Симлинки
  `.venv` и `node_modules` указывают на основной клон и продолжают работать.
- Пропускаются с объяснением: заблокированные (`locked`), без каталога (`prunable`)
  и те, чьё новое место уже занято. Если git отказал (например, в worktree есть сабмодули),
  wt-migrate сообщает об этом и переносит остальные.
- `--apply` не начнёт, пока шелл или открытая сессия agterm стоят в переносимом worktree:
  иначе они остались бы в удалённом каталоге. Сессии проверяются через `agtermctl`.
- Каталоги старой папки, опустевшие после переноса, удаляются через `rmdir`. Чужие пустые
  каталоги остаются.
- История Claude Code хранится по пути каталога (`~/.claude/projects/<путь>`). В новом
  месте `claude --continue` прежнюю сессию не найдёт, и `wt` запустит новую.

### Как работает wt

- **Какая репа.** Аргумент у `wt` один: постфикс, он же имя ветки. Репа определяется так:
  1. Текущий каталог, если он внутри git-репы. Из worktree берётся его основной клон,
     поэтому `wt` внутри worktree создаёт соседний worktree, а не вложенный.
  2. Иначе имя текущего воркспейса agterm (`agtermctl tree --json`): одноимённый клон
     ищется в `repos`.

  Не в git-репе и вне agterm или без подходящей репы `wt` завершается ошибкой.
- **База.** Базовая ветка берётся из `origin/HEAD`. Если его нет, используется первая
  существующая из `main`, `master`, `static-dev`, `develop`. `wt` делает `fetch` и
  перематывает локальную базу на origin:
  - основной клон на другой ветке: перемотка без checkout, рабочее дерево не трогается;
  - основной клон на самой базе: `merge --ff-only` в нём;
  - база разошлась с origin или дерево мешает перемотке: ветка создаётся от
    `origin/<база>`, `wt` печатает предупреждение.
- **Без upstream.** Ветка создаётся с `--no-track`. Иначе от `origin/main` git прописал бы
  upstream `origin/main`, и `git push` из фичи ушёл бы прямо в main. Вместо этого в репе
  включается `push.autoSetupRemote`: первый `git push` создаёт одноимённую ветку на origin.
- **Локальные файлы.** `.venv` и `node_modules` подключаются симлинками на основной клон,
  `.claude/settings.local.json` копируется.
- **Агент.** По умолчанию `claude --continue || claude` в текущей вкладке. После выхода
  из агента остаётся шелл внутри worktree. С `WT_NEW_SESSION=1` агент открывается
  в новой сессии agterm, и она не закрывается после выхода агента.
- **Уже есть.** Если каталог worktree существует, `wt` просто переходит в него.

`wtrm` перед удалением показывает незакоммиченные правки и незапушенные коммиты
и спрашивает подтверждение. Если вы стоите внутри удаляемого worktree, `wtrm` переходит
в основной клон.

### Переменные окружения

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `WT_CONFIG` | `~/.config/agterm-kit/wt.conf` | путь к конфигу |
| `WT_REPOS` | из конфига | каталоги с репами через `:` |
| `WT_AGENT` | `claude` | агент по умолчанию: `claude`, `codex`, `none` |
| `WT_CLAUDE_CMD` | `claude --continue \|\| claude` | команда запуска Claude Code |
| `WT_CODEX_CMD` | `codex` | команда запуска Codex |
| `WT_NEW_SESSION` | не задана | `1`: агент в новой сессии agterm |
| `WT_CLAUDE` | `1` | `0`: то же, что `WT_AGENT=none` (устаревшая) |

## ask

Когда агент предлагает варианты, вопрос открывается поверх его сессии HTML-страницей,
а не списком в терминале или текстом в чате. На странице видны все вопросы сразу,
описания вариантов и превью кода рядом с вариантом. Можно выбрать несколько вариантов
или вписать свой.

| Агент | Как подключено | Что делает агент |
|---|---|---|
| Claude Code | PreToolUse-хук `ask/ask-hook.sh` на `AskUserQuestion` | ничего нового: зовёт свой `AskUserQuestion`, хук возвращает ответ через `updatedInput.answers` ([документация](https://code.claude.com/docs/en/hooks#askuserquestion)) |
| Codex | MCP-сервер `ask/agterm-ask-mcp` с инструментом `ask_user` и правило в `~/.codex/AGENTS.md` | вызывает `ask_user` вместо вопроса в чате |
| OpenCode | тот же MCP-сервер и правило в `~/.config/opencode/AGENTS.md` | так же |
| omp | тот же MCP-сервер в `~/.omp/agent/mcp.json` | вызывает `ask_user` вместо вопроса в чате |
| скрипт, любой другой агент | CLI `ask/agterm-ask` | `agterm-ask "Вопрос?" "Да" "Нет"` печатает выбранный вариант |

Почему для Codex и OpenCode MCP, а не хук: их хуки не умеют подставить ответ за инструмент
вопроса. У Codex PreToolUse-хук может разрешить, запретить или переписать вызов, но не вернуть
результат. У OpenCode у плагинов нет событий вопроса. MCP-сервер работает у обоих и запускается
вне песочницы агента, поэтому дотягивается до сокета agterm.

### Управление

| Клавиша | Действие |
|---|---|
| `1`…`9` | выбрать вариант в текущем вопросе; номер после последнего варианта ставит курсор в поле «Свой вариант…» |
| `↑` `↓` | перейти между вариантами и вопросами |
| `Enter`, `Space` | выбрать вариант под фокусом |
| `⌘↩` | отправить ответ, когда отвечены все вопросы |
| `Esc` | закрыть страницу без ответа |

Один вопрос с одним ответом отправляется сразу по выбору, как `Enter` в терминале.
В вопросах с несколькими ответами варианты переключаются, а свой вариант добавляется
к выбранным через запятую.

### Установка

Нужны agterm с HTML-оверлеями (проверено на 0.34.0) и jq. `install.sh` из раздела про `wt`
ставит и `ask`:

- создаёт `~/.config/agterm-kit/ask.conf` из `ask/ask.conf.example`, если конфига ещё нет;
- **Claude Code:** прописывает хук в `~/.claude/settings.json` (или в
  `$CLAUDE_CONFIG_DIR/settings.json`) с matcher `AskUserQuestion` и таймаутом 3600 секунд.
  Запись с этим хуком остаётся ровно одна: дубли и записи с другим matcher или таймаутом
  заменяются правильной, остальные хуки не трогаются;
- **Codex**, если есть `~/.codex` (или `$CODEX_HOME`): ведёт в `config.toml` блок между
  строками `# agterm-kit:ask begin` и `# agterm-kit:ask end` с сервером `agterm-ask`. В блоке:
  - `env_vars` с переменными `AGTERM_*`: Codex пускает к stdio-серверу только переменные
    из белого списка, без них сервер не знает, в какой сессии открыть страницу;
  - `tool_timeout_sec = 3600`: по умолчанию Codex ждёт инструмент 60 секунд;
  - `approval_mode = "approve"` для `ask_user`: инструмент только спрашивает пользователя,
    отдельное подтверждение перед вопросом лишнее.

  Повторный запуск обновляет содержимое блока. Сервер `agterm-ask`, прописанный вручную
  без маркеров, не трогается;
- **OpenCode**, если есть `~/.config/opencode`: добавляет сервер в `opencode.json`. Флаг
  `enabled`, выставленный вручную, сохраняется. `opencode.jsonc` с комментариями не трогается:
  OpenCode сливает `opencode.json` и `opencode.jsonc` из одного каталога, поэтому сервер
  ложится в `opencode.json` рядом. Если `agterm-ask` уже прописан в `.jsonc` вручную, установка
  его не дублирует;
- **omp**, если есть `~/.omp/agent`: добавляет сервер в `mcp.json` и сохраняет выставленный
  вручную флаг `enabled`. Таймаут инструмента — 3600 секунд. Если `mcp.json` — симлинк,
  которым управляет `omp-setup`, установщик не меняет его и печатает готовый JSON-фрагмент;
- **правило для Codex и OpenCode** в их глобальный `AGENTS.md`, между строками
  `<!-- agterm-kit:ask begin -->` и `<!-- agterm-kit:ask end -->`: просить выбор через
  `ask_user`, а не текстом. Одного описания инструмента не хватает: без правила Codex видит
  `ask_user`, но всё равно спрашивает в чате (это поймал `make eval`).

JSON-конфиги меняются атомарно: новая версия пишется во временный файл рядом и заменяет
старую переименованием, прежняя сохраняется как `<файл>.bak.<время>`. Симлинк (например,
в репозиторий dotfiles) остаётся симлинком, права файла сохраняются. Если менять нечего,
файл не трогается и бэкап не создаётся.

Хук и сервер указывают на скрипты в клоне репозитория, так что после `git pull` новая версия
работает сразу. Правку `settings.json` Claude Code замечает сам. Codex и OpenCode читают
MCP-серверы при старте: уже запущенные сессии увидят `ask_user` после перезапуска.

## Стадии работы и доска

Задача идёт по стадиям: **анализ** (разбор требований) → **план** → **выполнение** → **ревью** →
**MR** (и разбор замечаний) → **готово**. Под каждой сессией Claude Code в сайдбаре agterm видно
стадию и короткую сводку, что происходит сейчас:

```
◈ План · раздаю задачи 3/7
```

Доска (**Ctrl+Shift+K** или «Доска стадий» в палитре) показывает все такие сессии колонками по
стадиям. Карточки обновляются каждые 2 секунды: имя сессии, сводка, проект, папка (у worktree это ветка), статус агента
(зелёный — работает, янтарный — ждёт вас). Клик переходит к сессии, `/` ищет по имени и сводке.
Сессии, которые ждут ответа, поднимаются наверх колонки, а счётчик «ждут вас» в шапке ведёт к первой.

### Откуда берётся стадия

- **Скилы.** Хук `PreToolUse` на `Skill` и слэш-команды в промпте переключают стадию сами:
  `brainstorm`, `grilling`, `research`, `diagnosing-bugs`, `kaiten`, `allure-triage` → анализ;
  `planning:make` → план; `planning:exec`, `plan-dispatch`, `tdd` → выполнение;
  `review-refactor`, `code-review`, `gpt-review`, `simplify`, `security-review` → ревью;
  `gitlab-mr`, `pr` → MR.
- **Команды.** Успешные `glab mr create`/`gh pr create` → MR, `glab mr merge`/`gh pr merge` → готово.
  Их ловит `PostToolUse`, поэтому отклонённый или упавший вызов стадию не меняет.
- **Агент.** Хук `SessionStart` сообщает агенту, как отмечать стадию и сводку:
  ```sh
  stages/agterm-stage set analysis "разбираю требования из карточки"
  stages/agterm-stage note "задача 4/7: тесты на парсер"
  ```
  Песочница Bash не пускает агента к сокету agterm и в `~/.local/state`, поэтому эту команду
  применяет хук `PostToolUse`: он видит её в Bash и работает вне песочницы. Сама команда в
  песочнице завершается с кодом 0. Хук принимает только `set`, `note` и `clear` в начале
  команды; перенаправления в сводку не попадают, а текст с `$(…)` пропускается.

Побеждает последняя запись. Повторный скил той же стадии (второй `/code-review`) сводку агента
не стирает.

### Команды

Путь от корня kit, в `PATH` команда не ставится:

```sh
agterm-stage set <стадия> [сводка]   # analysis|plan|exec|review|mr|done или по-русски: анализ, план…
agterm-stage note <сводка>           # сводка без смены стадии
agterm-stage get [--json]            # стадия этой сессии
agterm-stage clear                   # убрать стадию и строку
agterm-stage restore                 # вернуть строки в сайдбар после перезапуска agterm
agterm-stage board                   # открыть доску или перейти к ней
```

Состояние каждой сессии лежит в `~/.local/state/agterm-kit/stages/<id сессии>.json`: стадия,
сводка, источник, время начала стадии и история последних 50 переходов. Записи сессий, которых
нет в agterm дольше 14 дней, удаляются.

### Как устроено

Строка под сессией — это `agtermctl session info --markdown`. Доска — HTML-страница
`stages/board.html` с `--js` поверх отдельной сессии «Доска»: она читает `agterm.request('tree')`
и берёт из строк info стадию и сводку, поэтому своего сервера и файла данных у неё нет.
agterm не хранит строки info после перезапуска, их возвращают хук `SessionStart` и сессия доски,
которая раз в минуту вызывает `restore`. Сессия доски закреплена через `session restore`,
поэтому после перезапуска поднимается снова. Закрыли страницу — Enter в сессии доски
открывает её заново.

Открыть `stages/board.html` в браузере вне agterm: страница покажет демо-данные.

Установка: `make install-gui` (хуки Claude Code и клавиша). После неё нужна новая сессия
Claude Code и `agtermctl keymap reload`. Хук всегда завершается с кодом 0, а в настройках
записан с `|| true`: сбой или переезд kit не мешает агенту вызывать инструменты. Работает только с Claude Code: у Codex и OpenCode
нет хуков на скилы.

## lb-limits

Claude Code ходит через балансер agent-lb, а встроенные виджеты ccstatusline (`session-usage`,
`weekly-usage`) показывают лимиты одного аккаунта. `lb-limits/lb-limits` печатает лимиты всего
пула, те же, что в блоке «Pool details» дашборда:

```
Claude 1/2 · 5h 79% 2h 39m · wk 83% Fri 17:00
```

`1/2`: сколько аккаунтов пула могут взять работу из скольких. `5h` и `wk`: остаток пятичасового
и недельного окна и время до сброса (для месячных пулов `mo`). Округление, формат времени и
цвета (больше 30% зелёный, от 10% жёлтый, ниже красный, `Out` при исчерпании) взяты из дашборда.

### Установка

```sh
./install.sh                          # создаст ~/.config/agterm-kit/lb-limits.conf из образца
$EDITOR ~/.config/agterm-kit/lb-limits.conf   # password_file: файл с паролем дашборда
lb-limits/lb-limits refresh           # проверка: 0 и пусто в stderr
lb-limits/lb-limits ccstatusline      # заменить виджеты лимитов в ccstatusline
```

`lb-limits ccstatusline` заменяет в `~/.config/ccstatusline/settings.json` виджеты
`session-usage`, `reset-timer`, `weekly-usage`, `weekly-reset-timer`, `weekly-opus-usage` и
`weekly-sonnet-usage` одним `custom-command` на месте первого из них, лишние разделители
убирает. Прежний файл сохраняется в `settings.json.bak.<время>`, повторный запуск ничего не меняет.
Если таких виджетов нет, лимиты дописываются в конец первой строки. Перезапуск Claude Code не нужен:
ccstatusline перечитывает настройки при каждой отрисовке.

### Конфиг

`~/.config/agterm-kit/lb-limits.conf` (другой путь задаёт `LB_LIMITS_CONFIG`), строки `ключ=значение`,
образец `lb-limits/lb-limits.conf.example`:

| Ключ | По умолчанию | Что |
|---|---|---|
| `url` | `http://127.0.0.1:2455` | адрес agent-lb |
| `pool` | `anthropic-general` | id пула из `GET /api/pools` |
| `password_file` | нет | файл `KEY=VALUE` с паролем дашборда, например `.env.local` рядом с docker-compose |
| `password_key` | `CODEX_LB_DASHBOARD_PASSWORD` | ключ пароля в этом файле |
| `ttl` | `60` | секунды между обновлениями |
| `label` | `Claude` для `anthropic-general`, иначе id | подпись перед лимитами |

### Как работает

`/api/pools` закрыт сессией дашборда, API-ключ клиента к нему не подходит. Скрипт входит через
`POST /api/dashboard-auth/password/login` и хранит cookie сессии в
`~/.cache/agterm-kit/lb-limits/cookie` (права 600). Пароль читается из `password_file` только
для входа и никуда не копируется. Когда сессия истекает, балансер отвечает 401, и скрипт входит заново.

ccstatusline ждёт команду 1 секунду, поэтому строка всегда печатается из кэша
(`~/.cache/agterm-kit/lb-limits/pools.json`). Если кэш старше `ttl`, в фоне запускается
`lb-limits refresh`; замок не даёт нескольким вкладкам опрашивать балансер одновременно.

Сообщения вместо лимитов:

| Строка | Причина |
|---|---|
| `lb: …` | первый запуск, кэш ещё пуст |
| `lb: нужен password_file` | балансер требует вход, а пароль не настроен |
| `lb: вход не удался` | неверный пароль; следующая попытка через 15 минут, чтобы не упереться в лимит попыток |
| `lb: нужен TOTP` | в дашборде включён TOTP, скрипт его не поддерживает |
| `lb: нет связи` | балансер не отвечает |
| `lb: нет пула <id>` | в ответе нет пула из `pool` |
| `… (12m назад, нет связи)` | цифры старше пяти обновлений: показаны последние известные и причина |

`NO_COLOR` отключает цвета.

## Статус omp в agterm

Расширение `omp/agterm-status.ts` обновляет статус сессии в сайдбаре agterm. При событиях
`agent_start` и `turn_start` оно ставит `active --blink`, при `agent_end` — `completed`.
Вызов проходит через `omp/agterm-status.sh`: без `AGTERM_ENABLED=1` скрипт ничего не делает,
а ошибка адаптера статуса не прерывает omp.

Установка использует `HOME` из окружения и не меняет конфиг, которым владеет `omp-setup`:

```sh
./omp/install.sh
```

Скрипт создаёт симлинки в `~/.omp/agent/extensions/`: omp сам подхватывает этот каталог,
поэтому `config.yml` правка не нужна. Повторный запуск не создаёт дубли.

### Конфиг

`~/.config/agterm-kit/ask.conf` (другой путь задаёт `AGTERM_ASK_CONFIG`), формат как у `wt.conf`:

```ini
enabled = yes   # no: оверлей выключен, агенты спрашивают как обычно
follow = no     # yes: переключить agterm на сессию агента, когда он задаёт вопрос
size = 80       # ширина панели в процентах; 0 или 100: на всю сессию
agents = all    # или список: claude, codex, opencode, cli
```

`agents` выбирает, каким агентам показывать оверлей. Остальные спрашивают как без него:
Claude Code в терминале, Codex и OpenCode в чате. `cli` означает прямой вызов `agterm-ask`.

С `follow = no` страница открывается в сессии агента и ждёт, пока вы на неё перейдёте.
Статус сессии в сайдбаре при этом выставляют ваши обычные хуки agent-status, если они есть.

### Когда оверлея нет

После перезапуска agterm долгоживущий MCP-сервер иногда хранит старый `AGTERM_SESSION_ID`.
При ответе `no such session` ядро один раз восстанавливает привязку: ищет стабильный
`AGTERM_PANE_ID` среди всех открытых окон, затем единственную локальную сессию с точным
совпадением рабочего каталога MCP-процесса. При нескольких совпадениях или ошибке
инвентаризации восстановление запрещено. `active` никогда не используется как запасной
адрес. При успешном восстановлении новый ID записывается в stderr. Если каталог изменился
и стабильная панель не найдена, перезапустите MCP-клиент из нужной сессии.

Ничего не ломается: агент спрашивает как обычно. Claude Code показывает свой вопрос
в терминале, Codex и OpenCode получают от `ask_user` объяснение и спрашивают в чате.
Так происходит, если:

- агент запущен вне agterm (нет `AGTERM_ENABLED`), `enabled = no` или агента нет в `agents`;
- в сессии уже открыт другой оверлей, или `agtermctl` недоступен;
- страницу закрыли: `Esc`, кнопка «В терминале», `⌘W`;
- ответ не прошёл проверку: на каждый заданный вопрос нужна непустая строка;
- агент перестал ждать: таймаут хука (час), отмена вызова в Codex или OpenCode, выход агента.
  Тогда `agterm-ask` закрывает свою страницу. agterm закрывает оверлей только по сессии,
  поэтому сначала проверяется, что в слоте именно эта страница.

Причину `agterm-ask` пишет в stderr. В Claude Code она попадает только в debug-лог
(`claude --debug`), в Codex и OpenCode приходит агенту в тексте результата `ask_user`.

### agterm-ask

Ядро, которое используют хук и MCP-сервер, работает и само по себе:

```sh
ask/agterm-ask "Пушить в main?" "Да" "Нет, сначала PR"     # печатает выбранный вариант
ask/agterm-ask --context "deploy" < questions.json         # JSON в формате AskUserQuestion
```

На входе от 1 до 4 вопросов, в каждом от 1 до 9 вариантов. На выходе
`{"answers": {"<вопрос>": "<ответ>"}}`. Коды выхода: 0 ответ, 1 ошибка во входе,
2 страницу закрыли, 3 оверлей недоступен. `agterm-ask --help` показывает формат целиком.

Каждый вопрос оставляет строку в `~/.local/state/agterm-kit/ask.log` (путь меняет
`AGTERM_ASK_LOG`, пустое значение отключает журнал): время, агент, исход
(`answered`, `dismissed`, `cancelled`, `unavailable`, `error`), секунды ожидания и число
вопросов. Текст вопросов в журнал не пишется. Сколько вопросов прошло через оверлей:

```sh
cut -f2,3 ~/.local/state/agterm-kit/ask.log | sort | uniq -c
```

### Безопасность страницы

Страница открывается с `--js`, потому что собирает ответы на несколько вопросов в один.
Страница с JavaScript может вызывать команды agterm, поэтому текст от агента на неё
вставляется только как данные: JSON-блок, в котором каждый `<` заменён на `\u003c`,
отрисовка через `textContent`. Разметка в вопросе показывается текстом и не исполняется.

## Разработка

```sh
make test     # bats: wt, ask, stages, lb-limits и install.sh с поддельными agtermctl и agent-lb
make lint     # zsh -n и shellcheck
make hooks    # pre-commit: lint и тесты перед каждым коммитом
make eval     # платный eval ask на настоящих Codex и OpenCode, нужен agterm
```

`make eval` (`evals/ask-agents.sh [-n прогонов] [-t порог%] [codex] [opencode]`) даёт агенту
задачу, где нужно спросить пользователя, и сам отвечает за пользователя вторым вариантом
через `agtermctl session overlay submit`. Прогон засчитан, если страница появилась и агент
назвал выбранный вариант. Отчёт лежит в `/tmp/agterm-ask-eval/<время>/report.tsv`.
Перезапускайте eval после обновления агентов и после правок описания `ask_user`.

Тесты изолированы: временный `HOME`, git без пользовательского конфига, локальные bare-репы
вместо origin, `agtermctl` подменён скриптом, который пишет вызовы в лог. Сеть и настоящий
agterm не нужны. Для запуска поставьте [bats-core](https://github.com/bats-core/bats-core)
(`brew install bats-core`) и shellcheck.

Структура:

```
wt/wt.zsh            функции wt, wtl, wtrm и дополнение для zsh
wt/wt.conf.example   образец конфига
ask/agterm-ask       ядро: вопрос в оверлее, ответ в stdout
ask/ask-hook.sh      хук AskUserQuestion для Claude Code
ask/agterm-ask-mcp   MCP-сервер с ask_user для Codex и OpenCode
ask/ask.html         шаблон страницы с вопросами
ask/ask.conf.example образец конфига ask
lb-limits/lb-limits  лимиты пула agent-lb для ccstatusline
stages/agterm-stage  стадии работы: команда, хук Claude Code, доска
stages/board.html    канбан-доска сессий по стадиям
install.sh           установка симлинка, конфигов, хука и MCP-серверов
evals/               платные evals на настоящих агентах
tests/               bats-тесты
```

Новая утилита получает свой каталог рядом с `wt/`, свои тесты в `tests/` и раздел в этом README.

## Темы Rex

`make install-themes` импортирует темы из установленного Rex Beta и добавляет команды
`Rex: <название>` в палитру пользовательских команд agterm. Выбор цвета не меняется до
запуска команды темы. `Rex: вернуть тему agterm` убирает цветовые переопределения.
Подробности, ограничения sRGB и проверки: [themes/README.md](themes/README.md).

Проверка восстановления диалога на живом agterm: `evals/ask-session.sh` из каталога
с единственной соответствующей сессией. Он подставляет заведомо устаревший ID и просит
реальный ответ; порог 100%, журнал и отчёт в `/tmp/agterm-ask-session-eval.*`.
Диагностика и правила безопасного восстановления: [docs/ask-session-recovery.md](docs/ask-session-recovery.md).
